# Оргструктура и область видимости данных — дизайн первого UI-пакета

Дата: 2026-09-08.

Статус: состав первого пакета согласован пользователем; письменный дизайн подготовлен для проверки перед планом реализации. Реализация ещё не выполнена.

Основание: [каноническое ТЗ](../../technical-specification.md), FR-IAM-02/04/05, FR-ADMIN-01/02, FR-I18N-04 и AC-02/06; [ADR-0013](../../adr/ADR-0013-data-scope.md), [ADR-0014](../../adr/ADR-0014-unified-open-source-runtime.md), [руководство модулей](../../guidelines/module-development-guide.md). Документ описывает реализацию выбранного пакета, не заменяет нормативные требования. Локальные audit-черновики не являются его нормативным основанием.

## 1. Результат и границы

Администратор сможет пройти через UI законченный сценарий: создать дерево организации, назначить сотруднику подразделения, задать роли правило видимости и проверить вычисленный доступ сотрудника. Пользователь только с правом просмотра увидит разрешённые сведения без возможности изменения.

В пакет входят:

- пункт «Оргструктура» в группе IAM и lazy-страница `/iam/org-units`;
- создание, чтение, редактирование, перенос и удаление организационных узлов;
- отдельная панель подразделений и вычисленной области в карточке существующего пользователя;
- отдельная панель правила видимости в карточке существующей роли;
- недостающие API чтения текущих назначений и правила роли;
- проверки контрактов существующих операций, необходимые для безопасного UI;
- локализация, loading/error/empty/forbidden/pending, доступность клавиатуры и регрессии.

Вне пакета: персональные grants/effective form-action permissions, каналы связи/2FA, webhooks, участники проектов, админ-сессии, глобальный feature registry, переработка Tasks, модульный marketplace, новая модель ролей или данных, production rollout. Автоматических назначений, смены правил существующих ролей и миграции сотрудников при открытии страницы не будет. Права меняются только явным сохранением соответствующей формы уполномоченным администратором.

## 2. Выбранный подход

Выбран вертикальный пакет: серверный контракт → изолированные UI-панели → интеграция в shell/users/roles → проверки полного сценария. Только дерево не закрывает настройку доступа; общий рефакторинг навигации до этой функции не даёт пользователю законченного сценария. Поэтому глобальную архитектуру меню сохраняем, добавляя один проверяемый пункт.

Frontend размещается в `apps/web/src/app/features/iam/org-units/`:

- `org-units.models.ts`: типы узла, назначения, правила и вычисленного scope;
- `org-units-api.service.ts`: типизированный API поверх общего `ApiService`, без собственного HttpClient/interceptor;
- `org-units.component.*`: страница, загрузка дерева и выбранный узел;
- `org-unit-tree.component.*`: отображение и выбор узлов, без HTTP;
- `org-unit-editor.component.*`: редактор и его draft/pending/validation;
- `user-org-units-panel.component.*`: назначения одного `userId` и отдельный read-only результат вычисления;
- `role-scope-panel.component.*`: правило одного `roleId`.

Шаблоны и стили — в отдельных файлах. Новые панели владеют своими запросами и состоянием. Users/Roles передают идентификатор выбранной записи и не копируют внутрь собственных больших классов логику этих панелей. Feature-local компоненты переиспользуются внутри IAM; общий `shared` не становится складом доменной логики. Публичный экспорт feature ограничен двумя встраиваемыми панелями.

Backend остаётся в существующем `md`: controller → application services → repositories. Новые ответы описываются публичными DTO, не новыми nested repository records. Существующие URL и поля ответов сохраняются; новая схема БД для UI не планируется. Если проверка инварианта потребует изменения схемы, оно оформляется отдельно новой миграцией, старые миграции не переписываются.

## 3. Страница дерева

На широком экране — дерево слева и сведения выбранного узла справа; на узком — вертикально. Для дерева используются вложенные списки с именованными кнопками раскрытия (`aria-expanded`) и выбора, а не неполная имитация ARIA tree. Все действия доступны без drag-and-drop.

Узел показывает код, название, вид, родителя, A/P-состояние и порядок среди соседей. Сортировка: `orderNo`, затем `id`. Виды остаются расширяемой строкой: известные `company/region/branch/department` имеют локализованные подписи, существующее неизвестное значение сохраняется и отображается без подмены. Пользовательские названия и коды не переводятся.

Создание: при пустом дереве — явное создание корня; при существующем — создание дочернего узла выбранного родителя. Код задаётся при создании и затем не редактируется, что соответствует текущему API. Переименование, вид, состояние и порядок редактируются отдельно от кода.

Перенос: выбор нового родителя в форме с исключением самого узла и его потомков. Корень нельзя переносить под другой узел; перенос не создаёт второй корень. Сервер повторно проверяет инварианты независимо от UI. При редактировании без переноса родитель сохраняется.

Удаление: явное подтверждение с названием/кодом. Нельзя удалять узел с детьми или назначенными сотрудниками; учитываются и `md_user_org_units`, и legacy `md_users.org_unit_id`. Каскадного удаления ветки/сотрудников нет. Пустой незанятый корень можно удалить, после чего снова доступно создание корня. Ошибка конфликта не скрывает выбранную запись.

Обновление состояния A/P и перенос могут изменить видимость данных. Перед сохранением этих изменений показывается предупреждение; автоматического «исправления» назначений нет.

## 4. Панель пользователя и семантика данных

В карточке существующего пользователя появляется раздел «Подразделения и область данных». Он содержит два явно разделённых блока:

1. **Назначенные подразделения:** исходный набор `md_user_org_units`, редактируемый мультивыбором по дереву. Сохранение полностью заменяет набор; снятие всех назначений требует явного пустого массива. Неактивные узлы показываются с отметкой; существующие назначения не удаляются молча. Новое назначение неактивного узла допустимо по существующей модели, но UI предупреждает, что такое назначение может не давать видимости.
2. **Фактическая область данных:** текущее правило и вычисленные видимые подразделения, только для чтения. После записи перечитывается с сервера. Пустой список при ALL означает неограниченность правила, при SELF — отсутствие привязки этого правила к дереву; UI не пишет «нет доступа» в обоих случаях.

`md_users.org_unit_id` — отдельная legacy-привязка, участвующая в некоторых проверках. Новый GET возвращает её отдельным nullable полем; UI показывает её read-only с пояснением, что эта связь не изменяется редактором набора. Она не объединяется автоматически с `orgUnitIds` и не мигрирует при сохранении. Это исключает ложное обещание, что снятие checkbox удаляет все исторические связи пользователя.

Панель работает только с уже созданным пользователем. Создание пользователя, назначение его ролей и существующие поля Users не переделываются. Смена выбранного пользователя отменяет старые GET, очищает предыдущий draft и загружает новые значения после разрешённого закрытия несохранённой формы.

## 5. Панель роли

В карточке существующей роли — «Область данных» с четырьмя вариантами:

| Код | Подпись | Пояснение |
|---|---|---|
| ALL | Все данные | Не ограничивает данные оргструктурой; права на действия всё равно проверяются |
| SUBTREE | Свои подразделения и подчинённые | Область зависит от назначений конкретного пользователя |
| UNITS | Только свои подразделения | Без автоматического включения потомков |
| SELF | Только связанные со мной данные | Связь определяется правилами конкретной сущности, например участием в задаче |

Сохраняется действующая семантика: из активных ролей берётся самое широкое правило `ALL > SUBTREE > UNITS > SELF`. Роль без явной записи правила считается ALL; это не повод записывать ALL автоматически. UI поясняет, почему сужение одной роли может не сузить итоговую область человека с другой широкой ролью.

Перед изменением правила показывается старое/новое значение и предупреждение о влиянии на носителей роли. Кнопка сохранения доступна только после успешного чтения и при изменённом значении. Матрица form/action и её сохранение остаются независимыми; новый раздел не требует `rbac.roles.grant` вместо действующего `iam.org_units.assign`.

## 6. HTTP и разрешения

Базовый путь: `/api/v1/iam/org-units`. Все новые чтения требуют `iam.org_units.view`; пользовательские JWT/cookie/CSRF правила не изменяются.

| Операция | Метод и путь относительно базы | Permission action | Контракт |
|---|---|---|---|
| Дерево/узел | GET `/`, GET `/{id}` | view | Текущий ответ сохраняется |
| Создание | POST `/` | create | Текущий набор полей; серверная валидация |
| Изменение/перенос | PATCH `/{id}` | update | Отсутствующий parentId сохраняет родителя; явный null обрабатывается как запрос корня и проходит инвариант одного дерева |
| Удаление | DELETE `/{id}` | delete | Без каскадного удаления |
| Исходные назначения — новый | GET `/users/{userId}` | view | `{ userId, orgUnitIds: number[], legacyOrgUnitId: number|null }` |
| Назначения | PUT `/users/{userId}` | assign | `{ orgUnitIds: number[] }`, полная замена |
| Вычисленная область | GET `/users/{userId}/scope` | view | Существующие `rule`, `visibleOrgUnitIds` сохраняются |
| Правило роли — новый | GET `/roles/{roleId}/rule` | view | `{ roleId, rule }`, default ALL для существующей роли без записи |
| Правило роли | PUT `/roles/{roleId}/rule` | assign | `{ rule }`, текущая семантика сохраняется |

Новые GET и обслуживаемые UI операции проверяют существование пользователя/роли/узла до чтения default или записи; несуществующая запись — 404, а не выдуманная роль ALL или успешный пустой набор. Неизвестные enum/state, пустые после trim обязательные строки и некорректные идентификаторы дают контролируемую validation error, а не необработанный SQL 500. `orgUnitIds` должен быть массивом положительных IDs; повторы нормализуются. Отсутствующий/null набор не считается намеренным снятием всех назначений: для этого нужен `[]`. Это целевое ужесточение небезопасной неоднозначности существующего PUT, покрываемое отдельным contract test.

Конфликты дерева, занятый код и удаление используемого узла дают 409 с безопасным пояснением. Точные тексты отображаются через общий Problem Details UX, не через SQL/stack trace.

Sidebar и guard нового маршрута требуют view. Встроенная панель дополнительно требует доступности самой карточки Users/Roles по существующим правилам; не предоставляет обхода её доступа. Действия разделяются по create/update/delete/assign. Пользователь с view без assign видит read-only панель. Отсутствие UI-кнопки не заменяет серверную проверку.

## 7. Транзакции и проверка существующих инвариантов

Запись дерева/назначений/правила, пересчёт области и permissions version, audit должны завершаться атомарно. Для переноса ветки проверяется корректность пересчёта не только пользователей самой ветки, но и пользователей с SUBTREE, назначенных выше старого или нового родителя. Это критерий корректности, а не предположение о том, что текущий код его уже обеспечивает.

До добавления изменяющих UI-действий тестами проверяются: sparse PATCH не сбрасывает parentId; root/cycle invariants; отсутствующие IDs; ошибочный payload не меняет назначения; rollback; конкурентные переносы не создают цикл; пересчёт области затрагивает нужных пользователей. Минимальные исправления подтверждённых нарушений этих контрактов входят в пакет. Для структурных мутаций требуется транзакционная сериализация проверок и записи в PostgreSQL, действующая между экземплярами server, а не только Java synchronized. Конкретный lock contract фиксируется в implementation plan.

Новые ETag/revision поля и глобальная optimistic-locking схема не вводятся. Fresh GET при открытии редактора и запрет двойной отправки защищают UI от stale callbacks, но не обещают разрешение конфликтов двух администраторов: последовательные допустимые записи сохраняют last-write-wins семантику. Для дерева при этом инварианты всё равно обязательны.

## 8. Общий UX, жизненный цикл и локализация

- Независимые loading/error/retry состояния дерева, формы назначений и вычисленной области; ошибка не выдаётся за пустой успешный ответ.
- Пока исходное значение не загружено, сохранение запрещено. После ошибки записи draft сохраняется; повтор — явным действием.
- Pending блокирует повторную отправку, смену цели редактора и его закрытие. После завершения сохраняется один результат, поздний ответ другой записи не применяется.
- При dirty Cancel/Escape/смене выбранной записи/внутренней навигации — подтверждение; при попытке закрыть вкладку используется стандартное предупреждение браузера. После подтверждённого выхода drafts очищаются.
- Ошибкой владеет один слой: inline ошибки используют отключение дублирующего toast в ApiService. Успех — один toast и перечитывание актуальных данных. Ошибка post-save refresh сообщает «сохранено, не удалось обновить», не предлагает повторять уже успешную запись автоматически.
- Используются существующие shared button/modal primitives и дизайн-токены. Native forms, подписи полей, aria-describedby, именованные иконки, focus restore, доступный keyboard порядок; без нового собственного modal framework.
- Все статические строки — семантические `iam.org_units.*` / `iam.data_scope.*` ключи серверного RU registry и packaged fallback; существующие виды/имена узлов не теряются при переключении языка.

## 9. Приёмка

Backend TDD: direct HTTP permission/CSRF tests, round-trip новых GET/PUT, invalid IDs/payload, отказ без побочных эффектов; PostgreSQL integration tests для дерева, назначений, пересчёта и audit/version. Существующие auth/RBAC/task/file scope tests должны остаться зелёными.

Frontend: unit/component tests для каждого изолированного блока, отмены stale GET и смены id, отсутствия записи до чтения, read-only permissions, dirty/pending/retry и отличия assigned от effective. Существующие Users/Roles/Shell сценарии не должны измениться.

Browser: на отдельной синтетической установке создать ветки, назначить пользователя, изменить правило, проверить сохранённое состояние и разрешённую видимость задач; отдельно проверить узкую роль, server 403/409, keyboard flow и narrow viewport в двух темах. Мутационные тесты не используют рабочие данные `localhost:4200`.

Перед утверждением реализации: полный Maven verify; Angular suite/typecheck/build; i18n audit; релевантные E2E, architecture/docs/hygiene и whitespace gates. Результаты фиксируются по фактическому commit/runtime; зелёный unit suite не заменяет browser или production acceptance.

## 10. Поставка и откат

Работа в текущем `main` согласно указанию пользователя. Существующие dirty UI-файлы сохраняются; app-shell меняется только для нового пункта и соответствующих tests. Никакого автоматического включения внешних сервисов, push или deploy в этом пакете.

Реализация делится на проверяемые commits: API/read contracts и инварианты; feature-local UI; интеграция Users/Roles/Shell; E2E. После изменения кода Graphify обновляется локально. Generated outputs для коммита регенерируются только из чистого checkout выбранного source commit; локальные audit drafts не включаются.

Откат UI/API-пакета — возврат source без удаления пользовательской оргструктуры/назначений. Результаты явных административных изменений не отменяются незаметно откатом приложения. Если потребуется schema migration, перед её реализацией дополняется migration/rollback contract; в текущем дизайне изменения схемы не требуются.
